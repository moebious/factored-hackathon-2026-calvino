| 16 | 2026-10-02 | **Classifier text is team-generated; dataset transcripts are not model input.** Laya is calibrated, fine-tuned and evaluated on a labelled set of Spanish and Portuguese customer messages, drafted with an LLM from dataset scenarios (personas, transactions, complaints) and reviewed by hand, all labelled synthetic. | 17 | 2026-10-02 | **Workflow: stuck payments, end to end.** A customer whose payment or transfer is Declined, Pending or Reversed is taken through five stages: **explain** the status from the bank's records; **clarify** when the request is ambiguous; **act** on a pending or declined transfer (cancel or retry, simulated by the dataset adapter as an ISO 20022 cancellation request and its answer) under the Gate, with all three outcomes (allow, ask a person, block); **investigate** with a case file and a durable case when a person is needed; **follow up** on the case later. Unrecognised charges, disputes and fraud signals go to a person. Closes decision 5. Tier 0 gains durable cases, one offline flywheel turn, policy replay and a bare-LLM ablation; Tier 1 keeps the coworker agent, the verifier panel, the second adapter, the analytics tab and fine-tuning | Demand: Transaccional is the largest contact category, 240,056 of 686,296 calls (35%); 354,327 of 4,425,008 transactions (8.0%) are Declined, Pending or Reversed `[measured]`. Two human baselines exist: Transaccional calls and Transactions-category complaints (resolution days, SLA, compensation). Best ISO 20022 fit (pacs.002, camt.053/054, camt.027/029/056) and the only candidate that exercises every part of Calvino. Chosen on single-table volume and design fit: links between tables (calls to transactions within 7 days, web errors to transactions within 15 minutes) were tested against shuffled timestamps and are at chance, so the data cannot attribute a call to the transaction behind it. The pre-registered rule (TSD-006) was not applied because the data had been explored first; it is kept, marked superseded. **Note, after the full-data baseline:** Transaccional calls are already resolved on first contact 91.5% of the time `[measured]`, so the superseded rule's room-to-improve gate (G2) would have rejected this workflow; the decision stands on volume, grounding and design fit, and the problem statement changes: match the human rate on calls with zero unsafe outcomes at lower time and cost, and improve investigations, whose savings can only be projected | accepted |
| 18 | 2026-10-02 | **Policy engine details (TSD-001).** The Route compares `needs_human` (not its complement) on two thresholds: at or above `escalate_at` goes to a person, strictly below `act_below` the agent path may act, between them clarify; ties go to the safer side. The Gate blocks before it asks (fraud, repeated authentication failures, not the owner, ineligible status), then, when Laya scores are present, blocks on the injection score (so a manipulated request is never put in front of an approver), then asks for the remaining hard rules and amounts above the gate limit, then reads the other Laya scores. Missing or malformed inputs fail closed: Route to a person, Gate to block (missing Laya scores: ask or block, set by `gate.on_missing_scores`). Limits are two per-currency tables in `policy/v1.yaml` (hard rule and gate), labelled policy assumptions and set with round exchange rates close to the dataset's (about 17 MXN, 4,000 COP and 350 ARS per USD); thresholds are hypotheses until T-201. Every input the policy reads is stored in the `DecisionRecord`, so `replay_decision` can re-run it | Keeps probabilities in, deterministic verdicts out (decision 4) and makes AC-8 testable from the log alone. The dataset cannot ground limits: claimed amounts have the same native median in all four currencies `[measured]`. The Router no longer "fails open" when Laya scores are missing: the policy fails closed, and any rules-based fallback classifier belongs to the hub before it calls the policy | accepted |
| 19 | 2026-10-02 | **Tool security details (TSD-002).** The customer reaches a tool only through a `Session` the hub attaches in the MCP request context (a resolver injected into `create_server`); no tool has a customer or session argument, and unknown arguments are ignored. A confirmation token is bound to one customer, action, target payment, amount and currency, expires after five minutes and works once; the key comes from `CALVINO_CONFIRMATION_KEY` and the server refuses to start without it. Idempotency keys are scoped to customer and tool; the same key for another target is a conflict. Ownership, eligibility (Pending to cancel, Declined to retry, never fraud-flagged, transfers and payments only), tokens and idempotency live once in `BankTools`, so an adapter cannot forget them. Refusals carry stable ids (`TOOL-NOT-OWNER`, `TOOL-INELIGIBLE`, `TOOL-FRAUD-FLAGGED`, `TOOL-TOKEN-*`, ...). Used-token memory is per process; several server processes need a shared store (production gap). | decided |

| 21 | 2026-10-02 | **The verifier panel ("tribunal") can only veto.** It runs only on cases the Gate already sends to a person (`ask`); independent specialists (amounts and transaction, policy and eligibility, privacy, promises and tone) each return pass/fail per criterion from the evidence, without debate and without seeing each other; a fixed rule combines them: any failed criterion blocks or escalates with the findings, all-pass still goes to the person with the verdicts in the case file. Their verdicts are logged, so replay re-applies the rule to the logged verdicts. Agents earn autonomy only through a measured, signed new policy version (for example one narrow action class after high agreement with operators and zero unsafe outcomes), never by the panel's own vote. Tier 1 (T-402); tentative | Keeps "probabilities in, deterministic verdicts out" and replay (AC-8); an LLM panel is not repeatable (frontier judges agree about 95.7% `[vendor]`), can be persuaded by the customer's text, and has no accountable signer | accepted (tentative) |

## Alternatives considered and rejected

Recorded so they are not re-proposed without new information. Reopening one needs a new decision entry above.

| Alternative | Rejected because | Related decision |
|---|---|---|
| TypeSafe **Jev** as the System One model | closed, hosted API: customer text would leave the bank; can't be fine-tuned or recalibrated on our data | 2 |
| **Pi SDK** (TypeScript) harness alongside Python agents | a second language and runtime for one person to maintain; LangGraph covers the same hooks | 1, 13 |
| **QLoRA** for fine-tuning Laya | built for very large generative models; Laya is a 322M-parameter encoder, where full fine-tuning or LoRA is simpler and safer | 13 |
| **AWS Lambda** for the hub and Laya | CPU only, cold starts, about 1 GB of model to load; containers serve it with steady latency | 13 |
| **LLM-generated UI** (free-form generative components) | an LLM choosing the interface is the free-form behaviour Calvino avoids; a fixed card catalog chosen by Laya keeps the UI a verdict | 10 |
| **OpenBot / OpenDots machinery** (computer per agent, browser, terminal, sandboxes, Postgres, CopilotKit Intelligence) | too heavy to host for the demo, alpha software, and general-purpose computer access widens the attack surface of a banking agent; only the philosophy is kept | 11 |
| **Agentic verifiers** for every output | adds cost and latency and makes false-pass rates hard to measure; kept only as a risk-tiered panel for high-risk actions | 14 |
| Several **LLM agents debating** or negotiating verdicts | verdicts are combined by a fixed rule in the hub, never by a model; spokes don't talk to each other | 13, 14 |
| **Cloudflare Agents SDK** | not needed alongside LangGraph Deep Agents | 13 |
| **Gradio / Streamlit-only** demo as the final UI | doesn't show the thesis; kept only as a fallback if the card UI slips | 10 |
| **Card disputes as the ISO 20022 showcase** | card networks still mostly use ISO 8583; ISO 20022 fits payments and investigations better | 12 |
| Buying **calvino.sh** for the demo | `calvino.rubrica.dev` is already owned | 10 |
| Individual **ADR files** instead of this log | churn for a short project; this table records the same decision, reason and status | — |
| Renaming DESIGN.md to **SDD.md** | no benefit, link churn, and "SDD" also means spec-driven development; the file is labelled as the software design document instead | — |
| Classic **GitFlow**, `--no-ff` merges, Git LFS, shared aliases | see decision 7 | 7 |
| Training or evaluating classifiers on the **dataset transcripts** | 42 templated texts shared by every category; results would only measure the template | 16 |
| **Disputes** ("is this charge mine?") as the workflow | amounts on only 1,308 of 3,335 Transactions claims, in mixed currencies; weakest in the data analyst's matrix; kept as the path to a person | 17 |
| **Complaint follow-up** as the workflow | richest outcome data, but it never resolves anything automatically, so it shows the thesis least; absorbed as the follow-up stage | 17 |
| **Broken channel plus fraud shield** as the workflow | rests on linking web errors to transactions, which is at chance in this data | 17 |
| Attributing calls to transactions (TSD-006 amendment draft) | the 7-day link is at chance (1.48% observed vs 1.48% shuffled) | 17 |
| Calvino **moving money on its own** (refunds, provisional credit) | out of scope for an AI-first demo: only cancel or retry of the customer's own pending or declined transfer, under the Gate, simulated | 17 |
| Training Laya on the **complaints table** with LLM teacher labels (the September 29 planning draft) | complaint descriptions are 5 fixed texts, one per category `[measured]`; the model would learn the template | 16 |
| Laya's own label as the verdict, or **pacs.002 status codes** (ACCP, PDNG, RJCT) as routing verdicts | Laya answers several calibrated questions and the policy decides; pacs.002 codes already mean payment statuses in banking, so reusing them for routing would confuse a banker | 4, 18 |
| A tribunal or panel that **approves** gray-zone actions by vote | not replayable, open to persuasion, no accountable signer | 21 |
| **DSPy** "Noul" types, "ReAnchor" or "native System One primitives" | not standard or verifiable features; Laya plus a deterministic policy already gives typed, calibrated decisions | 2, 4 |
| Portuguese test data with **PIX, boleto** or BRL | the dataset has no Brazilian customers or BRL; Portuguese speakers are modelled as customers in Mexico, Colombia and Argentina | 16 |
| Unmeasured performance claims (**33 ms latency, F1 92% ES / 85% PT**) | never measured; we measured 0.33–0.38 s per Laya call on CPU; figures appear only with evidence labels | — |
